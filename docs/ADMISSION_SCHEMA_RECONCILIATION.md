# Admission schema reconciliation (repository evidence)

Production schema inspection was unavailable in this workspace. The following decisions use checked-in migrations and service queries only; they are not a production-schema certification.

| Conflicting object | Repository evidence | Intended relationship supported by repository | Decision |
| --- | --- | --- | --- |
| `students` / `student_profiles` | `schema/001_foundation.sql` creates the master `students` table. `schema/003_students_admissions.sql` creates profiles and makes attendance, fees, results, and parent links reference profile IDs. `schema/028_admission_student_master_fk.sql` changes `admission_applications.student_id` to reference `students.id`. | Master student record with a linked profile used as the identity for student-facing modules. | Keep both existing entities; do not add another student master. The migration history does not fully define the master/profile linkage fields used at runtime. |
| Permanent ID and sequence | `schema/023_permanent_student_ids.sql` adds the unique ID to `student_profiles`; 027 creates the annual sequence. `src/admission-enrollment.js` allocates from that sequence but inserts the ID on `students` too. | One issued ID shared by master and profile, backed by one yearly sequence. | Preserve the existing sequence; do not add a second allocator. Storage synchronization requires production/representative schema verification. |
| Admission applications | Schema 003 defines `admission_applications`; 015 defines the newer `admission_form_applications`. `src/server.mjs` uses an in-memory admission form service while `src/admission-enrollment.js` queries `admission_applications`. | Existing public form/review remains separate from staff-only existing-student migration. | Do not create a third table or silently copy applications. Durable enrollment wiring is not safe to change until the application table and mapping are confirmed. |
| Enrollment and guardian account | Enrollment service writes `student_enrollments`, profile linkage fields, and parent links; these exact definitions are absent from checked-in migrations. It resolves a parent by email and otherwise creates an account. | Existing parent links and enrollment records must be reused; contact data belongs to the profile relationship model. | Do not require parent email for a data-only existing-student migration. Do not alter durable first-time enrollment or invent missing columns until verified. |

The sibling branch `codex/admission-workflow-enhancement` adds a later 078 preflight contract. It requires the `students` master, `student_profiles.student_master_id` link, `student_enrollments` academic context, parent link/role tables, and admission linkage fields. Its report records `DATABASE_URL_MISSING`, so those checks did not verify production. Its enrollment code also formats IDs to three digits, which does not satisfy this task's required four-digit format and was not copied.

The sibling enrollment implementation resolves guardian accounts by normalized phone and treats email as optional, which demonstrates that email-only matching is not a necessary repository-wide rule. That implementation relies on later schema and service files absent from this branch, so the current durable enrollment path remains unchanged until its exact dependencies are brought in and tested against a representative schema.

The current checkout does not contain a disposable database fixture or a configured approved read-only production inspection session. Persistent enrollment writes therefore remain an explicit release gate. `previewExistingStudentMigration` accepts a repository-produced snapshot and performs no writes; it is not presented as a production data reader or migration result.
