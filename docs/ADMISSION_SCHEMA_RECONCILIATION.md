Production schema inspection was unavailable in this workspace. The following decisions compare this checkout's migrations and service queries with the sibling feature branch's later migration evidence; they are not a production-schema certification.

The sibling branch `codex/admission-workflow-enhancement` adds migration 078 with leadership permissions, admission idempotency fields, and uniqueness indexes. Its enrollment writer is useful evidence but not safe to copy as-is: it formats permanent IDs to three digits, while this feature requires four. Its prior release report records `DATABASE_URL_MISSING`, so the branch did not certify production schema.

This environment has no `DATABASE_URL` or `OSAAH_DATABASE_ADAPTER_MODULE`, and no local MySQL/TiDB or Docker executable was available for a disposable database. The tracked schema in this checkout stops at migration 030. The sibling/recovery copies provide evidence for the additive admission/enrollment contracts in 031, 038, 054, 059, and 078, but these files are not a verified, contiguous migration chain in this checkout and are not proof that any production database has applied them. A read-only production schema inventory workflow exists on the sibling branch, but the available GitHub CLI credentials are invalid, so it could not be dispatched from this workspace.

The staff registration and student-migration persistence adapters are implemented against the repository-supported master/profile/enrollment model, and migration 081 adds only operation audit tables. Their runtime wiring is disabled unless `OSAAH_ENABLE_DURABLE_ADMISSIONS=true`; do not enable it until the complete canonical migrations and the deployed schema have been reconciled, migration 081 has been placed after its verified prerequisites, and adapter queries have been exercised against a disposable TiDB-compatible database. This guard keeps deployments without the verified schema from attempting database-backed admissions writes. The migration preview is a database-backed dry run only when explicitly enabled; no production preview or student migration was run here.

The public admission integration remains on its existing in-memory flow. `src/admission-form.js` stores applications in a process-local `Map`; tracked migration 015 instead defines `admission_form_applications` with section JSON and no student master foreign key; the durable enrollment service reads the separate legacy `admission_applications` table. No tracked adapter persists the public form into either table or maps its status, official-use class, and student relationship transactionally. The public acceptance route therefore no longer delegates to the legacy enrollment service. It accepts an explicit public persistence adapter only when one is supplied to `createApp`; the default bootstrap supplies none. Establish and test the intended public application persistence contract before adding that adapter.

`previewExistingStudentMigration` remains the pure snapshot planner used by the database reader and its unit tests. No production migration or student write was executed. Before enabling durable admissions, verify the canonical migration chain and deployed schema, then run disposable-database integration checks for migration ordering, constraints, transaction rollback, locking/concurrency, and retry behavior. Review preview conflicts and recovery before any authorized production migration.
