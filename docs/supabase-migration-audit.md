## Evidence and limits

Inspected the clean `main` checkout at `4872f48`, complete `schema/001`–`schema/081` history, `docs/CURRENT_RUNTIME_DATABASE_REQUIREMENTS_MANIFEST.md`, application database repositories/services, environment references, package manifest, and test inventory. The supplied Supabase `information_schema` response contained no public columns or non-system schema table counts. That establishes only that no application tables were returned by those inspected queries; it is not proof that every object is absent.

The migration is a first-install baseline for an empty project. It does not replay old MySQL/SQLite migrations. It creates the fixed `sch_default_01` row only, with no fabricated student, parent, staff, class, payment, or result records. Do not run against an existing or unknown schema without a separately reviewed diff and backup.

## Migration history findings

- Migration 077 uses MySQL `UNIQUE KEY` and inline `KEY` syntax; the new baseline expresses these as PostgreSQL constraints/indexes.
- Migration 078 adds `admission_applications.enquiry_request_id` and `permanent_student_id` plus unique indexes. It also grants `admissions.write` to two roles. Columns/indexes are represented, and the permission grant runs only against matching role rows that already exist.
- Migration 003 originally targets admission `student_id` at `student_profiles`; migration 028 changes it to `students(id)`. The baseline uses the newer master-student target. Profiles remain a separate identity bridge (`student_profiles.student_master_id`), and `parent_student_links.student_id` remains a profile ID. Runtime enrollment depends on this distinction.
- Migration 078's unique enrollment key is preserved across school/student/year/term/current-state. PostgreSQL's default NULL-distinct behavior matches TiDB's allowance for multiple NULL key parts; production duplicate preflight is still required before any data import.
- Migrations 067/068 use MySQL SHA2-generated scope hashes; PostgreSQL expression unique indexes encode NULL and non-NULL mock labels with distinct prefixes, preserving that part of the scope identity.
- Migrations 049/053 contain divergent definitions/views for overlapping fee objects. The baseline uses the current durable Fee Hub/repository fields plus compatibility objects and is for an empty target only.
- Migration 079 has a specific legacy data repair; this baseline includes canonical and legacy attendance columns but performs no data backfill. Migration 080/081 current flags and student insurance column are present.

## RLS, authentication and parent privacy

The migration enables RLS and revokes `anon`/`authenticated` grants on application tables. Only `schools` is readable to those roles, with a policy restricted to `sch_default_01`. Server-side signed-cookie auth and permission checks remain the authorization boundary; the API uses private server credentials. The service role bypasses RLS and must never be put in browser code.

Parent access must continue requiring an active `parent_student_links` row, expected parent user ID, school, master/profile join, and non-test student. Staff access must keep role, permission, and assigned-class checks. Direct browser Supabase access is not supported by these policies. If introduced later, add a trusted mapping to `auth.uid()` and narrowly test cross-parent, cross-school, inactive-link, class, payment, and result denial.
