# Sidebar Placement Engine

The sidebar is generated by `src/sidebar-registry.js`. Future modules must register metadata once; they must not edit HTML or append to a navigation array.

```js
registerModule({
  moduleId: 'staff-performance',
  moduleName: 'Staff Performance',
  route: '/staff/performance',
  category: 'STAFF & HR',
  parentModule: 'staff-directory',
  priority: 65,
  icon: '★',
  allowedRoles: ['HR_OFFICER', 'HEADTEACHER'],
  requiredPermissions: ['staff.performance.read'],
  schoolTypes: ['PRIVATE'],
  subscriptionRequirements: ['PRO'],
  enabled: true
});
```

`category` is preferred. If it is omitted, the engine uses a parent module, route/module namespace, feature keywords, and finally `ADMINISTRATION`. Lower `priority` values appear first. `parentModule` creates a nested child without changing the category order.

`visibleSidebar()` applies enabled status, role, permissions, school type, subscription, feature availability, and entitlements on every generation. The server passes the authenticated user's context to this function; sidebar visibility is not authorization. Protected routes and APIs must continue to enforce server-side permissions.

Duplicate module IDs replace the earlier registration and are recorded in `SIDEBAR_DIAGNOSTICS` for development diagnostics. `LOGOUT` is reserved and always rendered last. Temporary registration tests should use a separate module array and must not be added to production registrations.
